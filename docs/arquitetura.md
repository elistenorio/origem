# Arquitetura

## Testes

Os testes unitários do backend ficam em `backend/tests/` e rodam com Jest (`npm test`). Eles cobrem as regras de negócio dos services (pedidos, avaliações, login e cadastro), as validações dos controllers e os middlewares de autenticação, perfil e erros. Cada `describe` leva o ID do caso do plano de testes (ex.: "TC09 - Quantidade em estoque fora da faixa permitida (HU-030, Cenários 3 e 4)"), para a saída do `npm test` mostrar os mesmos casos do documento. O banco não é usado: o service roda de verdade e o repository e o cache são trocados por funções falsas com `jest.mock`, que devolvem o que cada teste precisa. Assim o teste verifica só a regra de negócio. Disputas reais entre duas compras pela mesma peça dependem do banco e ficam para testes de integração. O teste do ADR-003 (`npm run test:acesso`) é diferente: chama a API já ligada, com o seed aplicado.

Os testes do frontend ficam em `frontend/tests/` e também rodam com Jest (`npm test`), configurado pelo `next/jest`, que usa o compilador do próprio Next para ler TypeScript. Eles cobrem o que no frontend é regra e não tela: o store do carrinho (somar a mesma peça sem duplicar a linha, limitar a quantidade ao estoque, remover e recalcular os totais) e as validações dos formulários de checkout, de peça e de perfil, além de funções auxiliares. Os casos do plano de testes seguem o mesmo padrão do backend (ex.: "TC37 - Quantidade acima do estoque ao adicionar e ao alterar (HU-016, Cenário 3, e HU-017, Cenário 3)"). Os testes rodam no Node, sem navegador: o `tests/setup-env.ts` cria um `localStorage` em memória para o `persist` do carrinho funcionar. Os componentes de tela ainda não têm teste; o que depende deles (por exemplo, a mensagem de carrinho vazio no checkout) é verificado nos testes de sistema.
